# MacBook“待核对”修复与双向实测

## 结论

0.2.3 / build 6 已安装到两台。MacBook 首次获得原本缺少的扩展日志，采用主机编号后可以编辑既有任务。用户实机确认：“待核对已消失，能打开编辑”。

这次通过的是扩展元数据首次初始化、两台在线时的自动同步和串行跨机编辑子项，不宣称生产级多设备故障恢复或微信自动接管完成。

## 改动

- 原生任务字段继续走系统提醒事项；iCloud Drive 专用目录同步带校验的不可变日志快照、编号和回收快照，不上传 Key 或微信会话。
- 显式选择主机初始化、第二台加入；本机先保存 operations/requests/trash/number-map 安全副本，禁止直接加入另一批独立任务。
- 初次加入采用主机已有编号；新建任务使用设备编号段（mini 1–999，book 1001–1999）。未知远端任务不再猜测编号。重复登记、编号冲突会停止修改。
- 每12秒检查同步；修改前重新导入。完整校验合并后再提交本机日志，保留原操作ID和因果父节点；不按文件时间覆盖状态。真正并发冲突继续保护。
- 每次读取原生任务时重扫专用列表，接收另一台增删/改名的分组。
- 增加确定性的“手动新增任务：标题”及“任务N进度40”入口，仍走持久请求、确认与执行流程，可不依赖模型管理任务。

## 实测证据

两机最终二进制 SHA256 均为 `bc5a4dac920fda5e796a807441a0aa7460088fb3e6d6c539dbe46e6e20b97f3b`。

1. mini 初始化时发布69条扩展日志、19个已有编号。系统资源状态实际返回 uploaded=true。book 起初不可见，用户在访达确认TaskCat目录后，下载完成并导入69条日志；没有使用SSH复制元数据文件。
2. 初始化后两端19项编号映射相同，book从原0条日志变为69条，无因果缺失或字段冲突。两端原5项待办的完整格式化查询哈希一致。
3. book通过真实App创建 `POC_DUAL_20261026_BOOK_EDIT`，分配1001；mini自动收到相同编号，成功更新进度40。
4. book再次执行完成操作时，其真实请求记录的beforeTask包含 progress=40、conflicted=false；确认后完成成功，mini实际查询到已完成。
5. mini创建 `POC_DUAL_20261026_MINI_EDIT`，编号20；book自动收到20，并成功确认完成。beforeTask.conflicted=false，复现此前跨机编辑失败场景并通过。
6. mini删除1001，book删除20。两端活动查询恢复5项，没有测试任务；两个删除操作对应的回收快照在两端均存在，操作ID相同。
7. 最终两端均76条日志、21个编号；分别对完整日志和编号映射排序后哈希比较，均完全相同。真实业务任务未有意改动；测试任务留在可恢复回收站。
8. 用户MacBook实机观察：原“待核对”消失，任务标题能打开编辑框；未要求保存真实任务修改。

243项自动化测试通过（11.70秒）。新增10项直接运行生产同步代码，覆盖首次合并、新任务编号、错编号段、重复编号、操作ID冲突、缺失父节点、损坏文件、设备登记冲突、并发进度冲突及离线编号分配。它们使用合成目录，不冒充真实断网/掉电实验。

## 尚未通过或当前限制

- 未实测两台断网并发修改、系统掉电、iCloud账户切换及全量重同步；首次下载可能延迟，不能给出送达上界或P95。
- 真正并发冲突不会自动覆盖；当前尚缺完整面向普通用户的冲突解决界面。
- 编号段每台999个新任务，登记冲突会暂停；自动续段尚未实现。
- 不可变云历史含回收快照；彻底删除任务不会清除既有历史。2000份快照/200MB上限，尚无自动压缩与全端历史清除。
- 现有两机已完整备份；旧备份恢复与已启用同步空间之间的全套兼容矩阵尚未验收。
- 微信保持mini原执行器；book未安装微信运行环境，没有双活、租约或自动接管结果。iCloud Drive不能当发送资格锁。
- 新临时签名仍可能触发一次提醒事项授权；模型/Bark日常读写继续使用本机文件，不访问钥匙串。
